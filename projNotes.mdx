 Think of every MDX page as four optional layers:

  1. File location decides its URL and section.
  2. YAML frontmatter describes the page to Starlight.
  3. Markdown contains the actual article.
  4. MDX imports, JSX, and JavaScript add features when needed.

  Most pages only need the first three.

  ## 1. Where new pages go

  Your documentation lives here:

  src/content/docs/
  ├── lab/
  ├── infrastructure/
  ├── code/
  └── notes/

  For example:

  src/content/docs/lab/active-directory-build.mdx

  becomes:

  /lab/active-directory-build/

  It also appears automatically under Cyber Range in the sidebar. You do not need to edit
  astro.config.mjs.

  Use lowercase, hyphenated filenames:

  good: active-directory-build.mdx
  good: gpu-passthrough-notes.mdx
  bad: Active Directory Build.mdx

  An index.mdx is the landing page for its directory:

  lab/index.mdx        → /lab/
  lab/windows/index.mdx → /lab/windows/

  ## 2. The standard new-page template

  For most Packet Foundry articles, start here:

  ---
  title: Building an Active Directory Lab
  description: Installing and validating a small Active Directory environment for security
  exercises.
  ---

  This page documents the environment, the decisions behind it, and the problems
  encountered during the build.

  ## Goal

  Build a small Windows domain suitable for authentication, attack-path, and
  defensive-monitoring exercises.

  ## Environment

  - Windows Server 2025
  - Windows 11 workstation
  - Proxmox virtualization
  - Segmented lab network

  ## Procedure

  1. Install Windows Server.
  2. Assign a static address.
  3. Install Active Directory Domain Services.
  4. Promote the server to a domain controller.

  ## Verification

  Run:

  ```powershell
  Get-ADDomain
  Get-ADForest
  ```

  Confirm that DNS resolution and domain authentication work from the workstation.

  ## What broke

  Document errors, failed assumptions, and the eventual solution here.

  ## References

  - [Microsoft Active Directory documentation](https://learn.microsoft.com/)

  That structure is enough for nearly every article:

  - Intro
  - Goal
  - Environment
  - Procedure
  - Verification
  - Problems encountered
  - References

  Use only the sections relevant to the page.

  ## 3. Frontmatter

  Frontmatter is the YAML between the opening --- lines:

  ---
  title: Building an Active Directory Lab
  description: Installing and validating a small Active Directory environment.
  ---

  title is required. Starlight displays it as the page’s <h1>, browser title, and sidebar
  label. Don’t add another # Page Title inside the article. Start with ordinary text and
  then ## headings. Starlight authoring guide
  (https://starlight.astro.build/guides/authoring-content/)

  description is strongly recommended. Search engines, social previews, and site metadata
  use it.

  Useful optional fields include:

  ---
  title: Experimental Detection Lab
  description: Testing Windows event collection and detection rules.

  # Hide the right-hand contents list.
  tableOfContents: false

  # Exclude the page from production builds.
  draft: true

  # Control its autogenerated sidebar entry.
  sidebar:
    label: Detection Lab
    order: 2
    badge: New
  ---

  Common options:

   Field                     Purpose
  ━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   title                     Required page title
  ────────────────────────  ──────────────────────────────────────
   description               Search and social description
  ────────────────────────  ──────────────────────────────────────
   draft: true               Development-only page
  ────────────────────────  ──────────────────────────────────────
   tableOfContents: false    Hides the right-hand contents list
  ────────────────────────  ──────────────────────────────────────
   sidebar.order             Lower numbers appear earlier
  ────────────────────────  ──────────────────────────────────────
   sidebar.label             Uses a shorter sidebar name
  ────────────────────────  ──────────────────────────────────────
   sidebar.badge             Adds labels such as New
  ────────────────────────  ──────────────────────────────────────
   sidebar.hidden            Keeps the page out of the sidebar
  ────────────────────────  ──────────────────────────────────────
   lastUpdated               Overrides the displayed update date
  ────────────────────────  ──────────────────────────────────────
   pagefind: false           Excludes it from search
  ────────────────────────  ──────────────────────────────────────
   template: splash          Wide landing layout without sidebars

  Regular articles should use the default doc template. template: splash is for unusual
  landing pages like /, not ordinary documentation. The complete set is in the Starlight
  frontmatter reference (https://starlight.astro.build/reference/frontmatter/).

  ## 4. Markdown you can use

  ### Headings

  ## Main section

  ### Subsection

  #### Smaller subsection

  Starlight creates anchor links automatically, and H2/H3 headings appear in the table of
  contents.

  ### Text

  This is **bold**, this is *italic*, and this is `inline code`.

  This is [a link to Code](/code/).

  ### Lists

  - First item
  - Second item
    - Nested item

  1. Install the package.
  2. Edit the configuration.
  3. Restart the service.
  4. Verify the result.

  ### Images

  ![Description of the screenshot](../../../assets/example.png)

  For images under public/:

  ![Packet Foundry logo](/logo.png)

  Always write useful alt text unless the image is purely decorative. Starlight processes
  local Markdown images through Astro’s image support. Starlight image documentation
  (https://starlight.astro.build/guides/authoring-content/#images)

  ### Code

  ```bash
  sudo systemctl status example.service
  ```

  Add a title when useful:

  ```ini title="example.conf"
  [server]
  enabled=true
  ```

  ### Callouts

  :::note
  This is supplementary information.
  :::

  :::tip[Useful shortcut]
  This is a faster way to complete the task.
  :::

  :::caution
  This configuration can interrupt network access.
  :::

  :::danger
  Do not run this against the host system.
  :::

  Starlight supports note, tip, caution, and danger. Starlight aside documentation
  (https://starlight.astro.build/components/asides/)

  ## 5. MDX components

  Imports go immediately after the frontmatter:

  ---
  title: Development Environment
  description: Tools used by the project.
  ---

  import { Card, CardGrid } from '@astrojs/starlight/components';

  <CardGrid>
    <Card title="Editor" icon="seti:neovim">
      Neovim with MDX language tooling.
    </Card>

    <Card title="Build system" icon="rocket">
      Astro and Starlight.
    </Card>
  </CardGrid>

  You can import your own Astro components:

  import SectionSplash from '../../../components/SectionSplash.astro';

  <SectionSplash
    theme="code"
    eyebrow="Packet Foundry / Code"
    intro="Tools and experiments built close to the work."
    focus="Utilities, automation, and systems experiments."
  />

  But regular articles should not use SectionSplash; that component is specifically for
  the four section index.mdx pages.

  Astro officially supports importing Astro and framework components into MDX. Astro MDX
  documentation (https://docs.astro.build/en/guides/integrations-guide/mdx/)

  ## 6. HTML and JSX

  You can write HTML-like JSX directly:

  <div className="custom-panel">
    <strong>Current state:</strong>
    <span>Operational</span>
  </div>

  In MDX:

  - Use className, not class.
  - Close tags such as <img />.
  - Capitalized tags such as <SectionSplash /> refer to imported components.
  - Lowercase tags such as <section> refer to HTML elements.
  - Don’t add <html>, <body>, or another <main>; Starlight already supplies them.
  - Avoid wrapping Markdown paragraphs inside <p> tags. Use <div> or <section> when the
    children contain Markdown blocks.

  ## 7. JavaScript and data

  You can export data near the top:

  export const hostname = 'domain-controller-01';
  export const address = '10.10.20.10';

  ## System

  - Hostname: `{hostname}`
  - Address: `{address}`

  You can also fetch build-time data:

  export const response = await fetch('https://api.example.com/status');

  export const status = response.ok
    ? await response.json()
    : null;

  Current API state: **{status?.state ?? 'Unavailable'}**

  Because Packet Foundry is statically generated, that request runs during astro build.
  The data changes only after another build.

  For browser behavior involving document, clicks, live API requests, or localStorage,
  put the script in an imported .astro component:

  import LiveStatus from '../../../components/LiveStatus.astro';

  <LiveStatus />

  That keeps build-time JavaScript and browser JavaScript clearly separated.

  ## The practical rule

  For a normal new page:

  1. Create it in the correct section.
  2. Add title and description.
  3. Write a short introductory paragraph.
  4. Start headings at ##.
  5. Use Markdown until Markdown becomes limiting.
  6. Import a component only when it solves a real presentation or behavior need.
  7. Run npm run build before considering it finished.

  Your existing src/content/docs/code/code-plan.mdx:1 is already a valid minimal page—you
  can simply expand it section by section as the work develops.
